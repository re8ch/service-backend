## B1 service observation

R640-host TCP requests to tenant-api Pod 10.42.13.232:19448 reached B1 and were
rejected by Cilium as `remote-node -> tenant-api`, `Policy denied`. The existing
policy permits selected pod namespaces and ingress identity. This is not proof
of a broken WireGuard tunnel or of failure from an authorized client. The Pod's
local readiness endpoint returned ready. No blanket policy allow was added.

## Confirmed public-mesh return-path defect

A query from FLK identity 10.250.0.105 to R640 DNS Pod 10.42.6.63 reached R640 on
wg-pt-a1. Its valid DNS answer left wg-public-mesh. FLK's R640 peer AllowedIPs
contained 172.31.92.128/32 and 10.250.0.128/32, but not 10.42.6.0/24, so the
return packet could not pass WireGuard's peer source-prefix validation.

FLK's A1/B1 per-Pod DNS tests passed; R640/MUBAO tests timed out. The assembler
only ran public-peer augmentation at startup and excluded relayNodes (MUBAO).
The correction is periodic source-prefix assembly from declared PodCIDR owners,
including relays, with an explicit ownership handoff to the new host controller.
No static route is required to conceal asymmetric cryptokey acceptance.

These are point-in-time observations, not fleet-wide acceptance or certification.

## RouterOS transit source defect

After public-peer source closure, FLK→R640 DNS passed. FLK→MUBAO still failed.
B1's route for the latter sends the flow to wg-cp-b1/RouterOS. The RouterOS B1
peer accepted only B1 transport/probe/node/Pod sources, excluding FLK identity.
A1's peer had an isolated extra LA2 identity, confirming inconsistent transit
source declarations. The new derived transit source contract covers all declared
spoke node/Pod sources on both route-server ingresses, with exact destination
control PodCIDRs and interface-pair firewall rules. It does not alter routes.
